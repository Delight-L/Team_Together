# AI Agent 기반 DB1 분석 시스템 역할·책임 설계서

## 1. 문서 목적

본 문서는 SeSAC08 최종프로젝트의 DB1 분석 시스템에서 **AI Agent와 데이터
처리·분석 모듈의 역할과 책임을 명확히 분리**하기 위한 기준 문서다.\
향후 Analysis 1·2·3을 함수화하고 자동화할 때 모든 분석 모듈은 본 설계의
공통 인터페이스와 운영 원칙을 따른다.

------------------------------------------------------------------------

## 2. 핵심 설계 원칙

### 2.1 Agent는 분석 계산기가 아니라 분석 관리자다

PCA, K-Means, 시계열 통계, 이상신호 계산 등 정량 분석은 검증된 Python
함수가 수행한다.\
AI Agent는 원천데이터의 갱신 상태와 검증 결과를 확인하고, 필요한 분석을
선택하여 실행하며, 결과의 상태·변화·경고를 관리한다.

### 2.2 분석 방법론과 Agent 판단을 분리한다

Agent가 임의로 Feature, PCA 축, 군집 수, 임계값 또는 분석 방법을
변경하지 않는다.\
방법론 변경은 사람의 검토와 코드·설정 변경을 통해 이루어지며, Agent는
승인된 분석 파이프라인을 실행한다.

### 2.3 Analysis 1·2·3은 독립 모듈로 유지한다

각 Analysis는 서로의 내부 구현에 직접 의존하지 않는다.\
공통 지역코드, 분석기간, 데이터 버전, 상태값 및 표준 결과 객체를 통해
연결한다.

### 2.4 데이터가 갱신되었다고 모든 분석을 다시 수행하지 않는다

Agent는 새로 들어온 데이터가 어떤 Analysis에 영향을 주는지 확인한 뒤
필요한 모듈만 실행한다.\
예를 들어 관심집단 월별 데이터만 갱신되었다면 Analysis 2 갱신을 우선
검토하고, Analysis 1의 구조적 Context는 불필요하게 다시 계산하지 않는다.

## 3. 전체 시스템 구조

``` text
                         ┌──────────────────────────┐
                         │ AI Agent / Orchestrator  │
                         │ 전체 분석 실행·상태 관리 │
                         └────────────┬─────────────┘
                                      │
                 ┌────────────────────┼────────────────────┐
                 ▼                    ▼                    ▼
          ┌─────────────┐      ┌─────────────┐      ┌─────────────┐
          │ Analysis 1  │      │ Analysis 2  │      │ Analysis 3  │
          │ 지역 Context│      │ 행동 시계열 │      │ 결제·상권   │
          └──────┬──────┘      └──────┬──────┘      └──────┬──────┘
                 └────────────────────┼────────────────────┘
                                      ▲
                         ┌────────────┴─────────────┐
                         │ Data / Validation Layer  │
                         │ API·원본·전처리·품질검증 │
                         └──────────────────────────┘
```

## 4. 계층별 역할과 책임

### 4.1 Data / Ingestion Layer

**책임** - 공공데이터 API 및 승인된 외부 데이터 소스 호출 - 원본
데이터(raw) 보존 - 수집 시점과 기준기간 기록 - 파일 형식 및 인코딩
처리 - 공통 행정동 코드 체계 연결을 위한 기초 처리 - 수집 성공·실패 상태
반환

**책임 아님** - 군집 수 선택 - 위험도 판단 - 분석 결과의 의미 해석

### 4.2 Validation Layer

**책임** - 필수 컬럼 존재 여부 - 데이터 타입 - 결측 및 중복 - 예상
행정동 존재 여부 - 기간 및 기준시점 - 구성비 및 값 범위 - 비정상적인 행
수 변화 - 필요 시 이전 데이터 대비 급격한 변화 - 분석 실행 가능 여부
판정

검증 결과는 최소한 `PASS`, `WARNING`, `FAIL` 상태로 구분한다.\
`FAIL`이면 기존 정상 결과를 덮어쓰지 않고 분석을 중단한다.

### 4.3 Analysis 1 --- 지역 구조 Context

**핵심 질문**\
"강남구 22개 행정동은 평소 어떤 구조적·활동적 특성을 가진 지역인가?"

**책임** - Analysis 1 입력 데이터 전처리 - 구성비 변수의 PCA 차원축소 -
13개 최종 Feature 구축 - 4개 Domain 균형화 - K-Means 후보 비교 - 군집
안정성 검증 - 최종 지역 유형 산출 - PCA 점수가 아닌 실제 원변수를 통한
Profile 재검증 - 이후 Analysis가 사용할 지역 Context 생성

**현재 고정된 4개 Domain** - A. 활동규모: `activity_intensity` - B.
생활활동구조: `active_pop_pc1`, `active_pop_pc2`, `time_structure_pc1`,
`time_structure_pc2`, `weekend_weekday_index` - C. 인구·가구구조:
`resident_age_pc1`, `resident_age_pc2`, `foreigner_ratio`,
`household_structure_pc1`, `household_structure_pc2` - D. 구조적
복지배경: `disability_ratio`, `livelihood_recipient_ratio`

각 Feature를 Z-score 표준화한 뒤 Domain 내부 Feature 수가 `n`일 때
`1/sqrt(n)` 가중치를 적용하여 네 Domain의 거리 기여도가 균형을 이루도록
한다.

**중요한 해석 원칙** Analysis 1의 군집은 사회적 고립 위험등급이 아니다.\
지역의 평상시 구조적 Context를 제공하여 Analysis 2·3에서 동일한 신호라도
지역 배경에 따라 다르게 해석할 수 있도록 지원한다.

### 4.4 Analysis 2 --- 행동변화·시계열 신호

**예정 역할** - 관심집단 등 월별 행동 데이터 관리 - 지역·집단별 시계열
구축 - 평상시 수준과 최근 변화 비교 - 행동 감소·증가 및 이상신호 탐지 -
변화의 크기·지속성·방향 기록 - Analysis 1 지역 Context와 연결 가능한
Evidence 생성

Analysis 2의 구체적인 Feature와 탐지 규칙은 별도의 Analysis 2 설계에서
확정한다.

### 4.5 Analysis 3 --- 결제·상권 및 생활경제 Context

**예정 역할** - 결제 데이터 전처리 및 분석 - 상권·업종 구조 분석 - 지역
생활경제 활동의 변화 또는 특징 파악 - Analysis 1·2 결과를 보완하는
생활경제 Context 생성

Analysis 3의 구체적인 분석 방법은 별도의 Analysis 3 설계에서 확정한다.

### 4.6 AI Agent / Orchestrator

**책임** - 데이터 갱신 여부 확인 - 수집 프로세스 실행 요청 - Validation
결과 확인 - 어떤 Analysis가 영향을 받는지 판단 - 필요한
`run_analysis*()` 함수 호출 - 실행 성공·실패·경고 관리 - 이전 결과와
신규 결과의 변화 확인 - 결과 버전 관리 지원 - Analysis 1·2·3 Evidence
연결 - 사람이 검토해야 할 상태 식별 - 대시보드 및 사용자 질의에 전달할
분석 Context 구성

**Agent가 하지 않는 것** - PCA 결과 임의 변경 - K-Means의 k 임의 변경 -
통계값 생성 또는 조작 - 검증 실패 데이터의 강제 반영 - 새로운 Feature의
임의 추가 - 분석 방법론의 자율적 변경 - 구조적 취약성을 사회적 고립
위험으로 자동 단정

## 6. Analysis 실행 정책

### 6.1 Analysis 1

새 데이터가 들어올 때마다 무조건 재군집화하지 않는다.\
Analysis 1은 상대적으로 구조적인 지역 Context이므로 관련 입력 데이터의
갱신과 유효한 변화가 확인되었을 때 재실행한다.

### 6.2 Analysis 2

월별 관심집단 등 시계열 원천데이터가 갱신되면 새로운 기간을 반영하여
실행할 가능성이 높다.

### 6.3 Analysis 3

결제·상권 데이터의 갱신주기와 분석 목적에 따라 실행한다.

Agent는 데이터셋과 Analysis 간 의존관계를 설정 파일 또는 명시적 규칙으로
확인하여 실행 대상을 결정한다.

------------------------------------------------------------------------

## 7. 공통 실행 인터페이스

각 분석 모듈은 가능한 한 동일한 호출 규칙을 갖는다.

``` python
run_analysis1(...)
run_analysis2(...)
run_analysis3(...)
```

Agent는 각 분석 내부의 세부 함수보다 위의 표준 진입점을 우선 호출한다.

공통 결과는 다음 정보를 포함하도록 설계한다.

``` text
analysis_id
status
data_period
data_version
validation
metrics
warnings
outputs
previous_version
change_summary
requires_human_review
```

이를 통해 Agent가 분석 종류와 관계없이 결과 상태를 동일한 방식으로
판독할 수 있도록 한다.

------------------------------------------------------------------------

## 8. 오류 및 Human-in-the-loop 원칙

다음과 같은 상황은 자동으로 기존 정상 결과를 대체하지 않고 사람의 검토
대상으로 전달한다.

-   필수 데이터 또는 컬럼 누락
-   행정동 코드 매칭 실패
-   심각한 결측 또는 중복
-   예상 범위를 크게 벗어난 값
-   데이터 정의 또는 스키마 변경
-   기존 결과와 매우 큰 구조 변화
-   군집 안정성 급락
-   singleton 등 기존에 없던 비정상 군집구조 발생
-   승인된 분석 설정의 변경 필요

Agent의 역할은 이러한 상황을 숨기거나 임의로 해결하는 것이 아니라
**원인과 영향을 구조화하여 사람이 판단할 수 있게 전달하는 것**이다.

------------------------------------------------------------------------

## 9. 데이터 및 결과 버전 관리

자동화 환경에서는 최신 결과만 저장하지 않는다.

권장 구조:

``` text
data/
├─ raw/
│  └─ YYYY-MM/
├─ processed/
│  └─ YYYY-MM/
└─ results/
   ├─ analysis1/
   ├─ analysis2/
   └─ analysis3/
```

각 결과에는 분석기간, 원천데이터 버전, 분석 설정 버전 및 실행시점을
추적할 수 있는 정보를 남긴다.\
새로운 분석이 실패한 경우 직전 정상 결과를 보존한다.

## 11. 개발 순서

1.  본 설계서를 기준 문서로 확정한다.
2.  공통 `config`와 `result_schema`를 설계한다.
3.  데이터 Validation 규격을 구현한다.
4.  Analysis 1을 독립적으로 실행 가능한 함수형 모듈로 구현한다.
5.  VSCode에서 Analysis 1 단독 실행을 검증한다.
6.  `requirements.txt`로 실행환경을 재현한다.
7.  Analysis 2 설계 확정 후 동일 인터페이스로 구현한다.
8.  Analysis 3 설계 확정 후 동일 인터페이스로 구현한다.
9.  마지막으로 Agent Orchestrator가 세 Analysis를 관리하도록 연결한다.
10. 자동 갱신·실패 복구·Human-in-the-loop 시나리오를 통합 테스트한다.

------------------------------------------------------------------------

## 12. 최종 원칙

본 시스템에서 **Python 분석 모듈은 재현 가능한 계산을 담당하고, AI
Agent는 계산의 실행과 상태를 관리한다.**\
Analysis 1·2·3은 서로 다른 질문을 담당하지만 공통 데이터 규격과 결과
인터페이스를 사용한다.\
이를 통해 새로운 데이터가 추가되거나 분석 모듈이 확장되더라도 전체
시스템을 다시 작성하지 않고 필요한 부분만 교체·추가할 수 있는 구조를
지향한다.
