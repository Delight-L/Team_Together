# 성능 개선 정리

> 참고: 본문의 `SqliteDb1Repository`·snapshot 경로는 이후 삭제되었고, 같은 조회 로직은 `SqlDb1Repository`(PostgreSQL 구현이 사용)에 남아 있습니다.

`backend`에서 v16 데이터 조회의 성능을 개선한 내용과 결과를 정리합니다.
**챗봇 구조와 답변 내용은 바꾸지 않았고**, 데이터 저장소 계층(`SqlDb1Repository`) 안에서만 고쳤습니다.
상세한 측정표는 [PERFORMANCE_COMPARISON.md](PERFORMANCE_COMPARISON.md), 재현 도구는 [tools/v16_bench/](tools/v16_bench/README.md)에 있습니다.

## 1. 요약

| 항목 | 개선 전 (원본 backend_old) | 개선 후 (backend) |
|---|---|---|
| 질문당 DB 연결 수 | 3 ~ 15회 | **1회** |
| 질문당 쿼리 수 (최대) | 304회 (이례적 변화 순위) | 39회 |
| 엔진 수준 11개 질문 합계 | 1,120 ms | **547 ms (2.0배, 51% 감소)** |
| 챗봇 답변 전체 7개 질문 합계 | 579 ms | **362 ms (1.6배, 37% 감소)** |
| 가장 크게 빨라진 질문 | 소비·지역 배경 107~315 ms | **9~26 ms (9~12배)** |
| 소비·지역 배경의 메모리 정점 | 27 MB | 0.3 ~ 1.9 MB |
| 출력 | – | **원본과 모두 동일** (18개 질문 × 5라운드 × 4경로) |

측정 조건: 실제 `db1.sqlite`(88개 테이블, 약 380MB), 질문마다 저장소를 새로 만듦(웹 서비스와 같은 수명), 질문당 15회 중앙값을 5라운드 반복, 같은 컴퓨터.

## 2. 무엇을 고쳤나

원본은 질문 하나를 처리하면서 **같은 일을 여러 번** 했습니다. 아래는 그 낭비를 없앤 방법이고, 모두 `agents/regional_v16/chatbot_agent/repository.py` 안의 변경입니다.

| # | 낭비 (원본) | 개선 | 효과 |
|---|---|---|---|
| 1 | 조회할 때마다 새 연결을 열고 «갱신 완료» 확인 쿼리를 실행 | 저장소 객체당 읽기 전용 연결 **1개를 재사용**하고, 확인은 연결을 열 때만 | 연결 3~15 → 1 |
| 2 | 같은 탐지·근거 표를 호출마다 전체 읽기·JSON 파싱·날짜 변환 | 요청 동안 **결과를 캐시**(표별 1회). 호출부에는 사본을 돌려줘 캐시가 오염되지 않음 | 반복 읽기 제거 |
| 3 | 같은 SQL·인자를 동·날짜·월 루프에서 반복, 테이블 존재 확인을 루프마다 실행 | 한 조회 안에서 **같은 SQL은 한 번만**(메모), 존재 확인은 1회 | 쿼리 수 감소 |
| 4 | 소비 원자료 테이블 3개(최대 10,560행)를 호출마다 **전부** 읽음 | 필요한 **기간(이전 분기·달 포함)·동·연령의 행만** SQL로 읽음 | 소비·지역 배경 **9~12배**, 메모리 27MB → 2MB 이하 |
| 5 | `activity(동, 기간)`이 호출마다 전체 표에 마스크를 만들고 재정렬 | 요청된 동의 행만 **정렬해 두고 날짜를 이진 탐색**(마스크·재정렬 생략). 동은 처음 요청될 때만 만듦 | 신호 목록·연령별 변화 단축 |
| 6 | 불변 공개본(`snapshots/` 아래)도 호출마다 변경 여부 확인 | 불변 파일은 **확인을 생략** | 확인 쿼리·`stat` 제거 |

### 안전장치 (속도 때문에 답이 바뀌지 않도록)

- **변경 감지**: 작업 DB는 `PRAGMA data_version`과 파일 크기·수정 시각으로 감지해, 바뀌면 연결과 캐시를 버리고 «갱신 완료»를 다시 확인합니다. 갱신 중이면 이전처럼 차단됩니다.
- **캐시 오염 방지**: 호출부가 결과를 바꿔도 캐시에는 영향이 없습니다(테스트로 확인).
- **동별 인덱스는 같은 표 위에서만 동작**: 날짜가 모두 해석되고 정렬 순서가 시간 순서와 같을 때만 이진 탐색을 쓰고, 아니면 기존 방식으로 처리합니다(날짜 표기가 섞인 경우를 테스트).
- **조건 내리기는 행 단위 dict인 소비 자료에만 적용**했습니다. 탐지 표는 행마다 JSON이라 일부 행만 읽으면 열 구성이 달라져 `row[key]` 접근이 깨질 수 있어서 **의도적으로 SQL로 내리지 않았습니다**. 대신 같은 표를 쓰는 인덱스(5번)로 같은 목표를 달성했습니다.
- **조회 순서 고정**: 여러 행을 돌려주는 조회 6곳에 기본키 순서의 `ORDER BY`를 명시했습니다. SQLite는 기본키 색인 순서로, PostgreSQL은 저장 순서로 돌려줘서 같은 SQL의 행 순서가 달랐기 때문입니다(실제 데이터로 PostgreSQL과 대조하다 발견). 실제 DB에서 원래 SQL과 행 순서가 같음을 전수 확인했습니다(2,452개 조합, 불일치 0).

### 단계별로 본 효과 (합성 DB: 동 22개, 6개월, 신호 27건)

신호가 많을 때 어느 개선이 얼마나 기여했는지 보려고 단계마다 같은 질문을 쟀습니다.

| 단계 | 신호 목록 시간 | 연결 | 쿼리 |
|---|---:|---:|---:|
| 개선 전 | 991 ms | 148 | 607 |
| + 연결 재사용·결과 캐시·중복 쿼리 제거 (1~3) | 286 ms | 1 | 46 |
| + 소비 조건 내리기·동별 인덱스·불변 확인 생략 (4~6) | 177 ~ 196 ms | 1 | 46 |

실제 데이터는 신호가 1건뿐이라 이 질문의 개선 폭이 작게(1.2배) 나왔지만, 신호가 많을수록 `_age_signal_changes`의 반복 호출이 늘어 합성 DB처럼 **큰 폭**(5배 안팎)이 될 것으로 봅니다. 이는 실제 데이터로 확인하지 못했습니다.

## 4. 왜 질문마다 차이가 나는가

| 질문 유형 | 개선 폭 | 이유 |
|---|---|---|
| 소비·지역 배경 | 큼 (9~16배) | 원본이 큰 테이블(`a3a_feature` 10,560행 등)을 통째로 읽었음. 필요한 행만 읽도록 바꾼 효과가 지배적 |
| 이례적 변화 순위 | 중간 (2.4배) | 원본이 같은 표를 12번 연결해 304회 쿼리. 연결·캐시 효과 |
| 신호 목록·동 변화 이유·연령별 변화 | 작음 (0.8~1.6배, 일부는 오차 범위) | 읽는 표(`a2_*`)가 132~660행으로 작아 읽기 자체는 싸고, 시간 대부분이 pandas 처리. **동 변화 이유와 연령별 변화는 원본보다 빠르다고 말할 수 없습니다**(이 컴퓨터에서 5라운드 범위가 겹쳐 «동일 수준»으로 해석) |
| 짧은 질문 (판정 기준, 지역 유형) | 2~3배 | 시간이 거의 연결·확인 비용이어서 연결 1회화의 효과가 상대적으로 큼 |

## 5. 성능에 불리하거나 확인하지 못한 점

| 항목 | 내용 |
|---|---|
| 메모리 | 탐지 표를 요청 동안 들고 있어 신호·연령 질문에서 약간 더 씀 (5 → 7MB, 답변 전체 기준 최대 8.7MB) |
| AI 모드 지연 | 유해 검사(moderate API)가 담당 선택과 **동시에** 실행되던 구조에서, 담당 선택 후 에이전트 안에서 **순차**로 실행되도록 바뀜. AI 모드에서 응답이 moderate 호출만큼 늦어질 수 있음. 이 지연은 측정하지 못함(외부 호출) |
| 작업 DB 경로 | 변경 감지 쿼리가 더해져 쿼리 수가 조금 많음(예: 신호 목록 24회 대 17회). 시간 차이는 대체로 오차 범위 |
| PostgreSQL | 로컬 서버에서는 SQLite snapshot과 같은 수준(합계 490 ms 대 474 ms). **원격 서버의 네트워크 지연은 측정하지 못함**. 질문당 쿼리가 4~40회라 왕복 시간이 직접 더해짐 |
| 데이터 규모 | 실제 데이터의 신호가 1건뿐이라 «신호가 많은 경우»의 개선은 합성 DB로만 확인함 |
| 측정 오차 | 질문에 따라 ±20~30% 흔들림. 범위가 겹치는 값은 오차 범위로 해석해야 함 |
| 측정용 데이터 | 받은 `db1.sqlite`에 없는 `pipeline_state`·`ctx_weather`를 SQLite 복사본에 추가·변환해 측정함(원본 파일은 수정하지 않음). PostgreSQL 경로는 **원본 파일을 수정 없이** 게시해 측정. 날씨의 눈 기록 상태(`snow_status`)는 복원하지 못함 |

## 6. 다음에 더 줄일 수 있는 곳

| 대상 | 내용 | 비고 |
|---|---|---|
| `_age_signal_changes` | 신호 행 × 연령대 5개마다 `activity()`를 호출(실제 데이터에서 136회). 동·월별로 한 번에 묶어 조회하면 호출이 크게 줄 것 | 질의 로직이라 구조 변경 필요. 신호가 많을수록 효과 큼 |
| `_load_frame`의 행 단위 `apply` | 신호 종류를 행마다 판정하는 `DataFrame.apply(axis=1)` | 벡터화는 가능하지만 NaN·None 처리까지 같은 결과를 보장하는 검증이 필요 |
| 동별 인덱스 생성 | 동마다 정렬하는 비용(동·연령대당 약 1ms) | 신호가 많아 거의 모든 동을 쓰는 질문에서 비중이 큼 |
| PostgreSQL 왕복 | 한 질문의 쿼리를 묶어서 보내기 | 원격 서버에서 효과가 클 가능성이 있으나 측정 후 판단 |
